# Phase 1 Review — architecture-fit lens
> Reviewer: harness-architecture-review · Date: 2026-05-19 · Phase 1 (independent, contract mode)

## Summary verdict
**ACCEPT-WITH-CHANGES**

The core direction (backend keeps run alive + reattach contract, additive wire,
double-gated by capability+flag) is right and proportionate for one-user-one-Mac.
All three wire-level claims I fact-checked against real code hold up. But the
contract has **two BLOCKER-class factual errors** that must be fixed before it can
serve as a locked阶梯 contract:

1. **ADR numbering is wrong** — contract says next = ADR-025; the repo's own
   `docs/adr/README.md` explicitly reserves **ADR-021** and ADR-023 as free and
   ADR-024 is latest. Next is **ADR-021**, not ADR-025. A contract that locks
   itself to a non-existent ADR slot is not actually locked.
2. **`waiting_workflow_choice` is architecturally unroutable as specified** —
   `vessel_workflow_paused` is emitted by a *separate subsystem* (M1C-A Workflow
   Engine) that has **no `runId`, is not in the `runs` map, and is
   `broadcastToAll`-ed by `workflowId`**. The C2/C3/C4 machinery is built
   entirely around the Eva `runs` (cli-runner subprocess) path. `reattach_run`
   keyed on `runId` cannot reach a paused workflow. This is a real
   cross-subsystem mismatch the contract papered over.

Plus 1 MAJOR (C5 timer-ownership claim is correct in intent but the contract
under-specifies the already-armed 590s timer) and 2 MAJOR resource/race holes
(C4 zombie-attached client, C3 abort-window-vs-reattach race). None are fatal to
the direction; all are fixable in a v0.2 of the contract.

## Findings

### F1. ADR numbering claim is factually false — contract locks itself to a non-existent slot — [BLOCKER]
**Where**: §0 ground-truth bullet ("ADR 顺接号: `docs/adr/vessel/` 现行为 3 位（ADR-019..ADR-024），下一 = **ADR-025**"); also §5 TTL table, §9 I-11, §12, all reference "ADR-025".
**Issue**: Fact-checked against `docs/adr/README.md:44-45`:
> `ADR-021 编号当前空闲，预留给 ADR-019 Steward 契约后续修订… 下次 Steward 契约修订用 021。`
> `ADR-023 编号当前空闲，留作后续使用。`

Filesystem confirms: `docs/adr/vessel/` contains ADR-000..ADR-020 (ADR-020 duplicated as a stray `ADR-020-pim-capture-entry 2.md`), then a **gap at 021/022/023**, then ADR-024 (latest accepted). ADR-022 was consumed by AISEP and removed during the `git filter-repo` split (`docs/BACKLOG.md:184`). So the actually-free, lowest, intended-for-reuse slot is **ADR-021** (README explicitly says 021 is reserved for "后续修订" / next contract, and 023 is also free). The contract's reasoning ("不采 skill 泛指的 4 位，遵已落地约定") is correct in spirit but lands on the wrong number — it never opened `docs/adr/README.md`, which is the canonical numbering ledger.
**Why it matters**: This is contract mode. A wire-protocol阶梯 lock whose ADR anchor points at a slot that (a) doesn't exist and (b) the repo's own ledger reserves the *predecessor* of for the next contract is not a locked contract — it will collide or orphan when ADR-021 actually gets written, and the dogfood gate (§11) + I-11 traceability break. Numbering errors in a "lock the contract" artifact are load-bearing.
**Suggested fix**: Change all `ADR-025` → **`ADR-021`** (or 023 if 021 is genuinely earmarked for Steward — but README line 44 reads as a soft reservation, and 023 line 45 is "留作后续使用"; pick one and cite `docs/adr/README.md` as the source of truth, not the directory listing). Add to §0 ground truth: "Numbering source = `docs/adr/README.md` ledger, NOT `ls docs/adr/vessel/`." Resolve the stray `ADR-020-pim-capture-entry 2.md` duplicate out-of-band (not this contract's job — flag only).

### F2. `waiting_workflow_choice` is unroutable: workflow engine is a separate runId-less subsystem — [BLOCKER]
**Where**: §3 C2 (`status: "waiting_workflow_choice"`, `pending: {kind:"workflow_choice"; workflowId; step; message; options}`); §2 C1 (`reattach_run` keyed on `runId`); §3 status-branch table row `waiting_workflow_choice`; §5 C4 `RegisteredRun.pending` workflow_choice variant; OQ-D.
**Issue**: Fact-checked against real code:
- `vessel_workflow_paused` is emitted in `packages/backend/src/workflow/executor.ts:161-167`: `broadcast({ type: 'vessel_workflow_paused', workflowId, step, message, options })`. It carries **`workflowId`, never `runId`**.
- `broadcast` is `broadcastToAll` (index.ts:368-373, injected at index.ts:385 `buildWorkflowRouter(broadcastToAll)`) — it fans out to **every** `wss.client`, it is not per-connection and not per-run.
- The workflow executor has **zero references to `runId`, `runs.set/get`, `RegisteredRun`, or `run-registry`** (grep confirmed). The M1C-A Workflow Engine is a wholly separate orchestration path from the Eva `runs` map (cli-runner subprocesses) that C3/C4/C5 are entirely built around. `runs` is `Map<runId, RunHandle>` (index.ts:434); `vesselRuns` is yet a third map (index.ts:449); workflows live in `workflow-store` keyed by `workflowId`.

So: a `reattach_run { runId }` cannot locate a paused workflow (no runId exists for it). `RegisteredRun.pending = {kind:"workflow_choice"...}` (§5) can never be populated because workflows don't create `RegisteredRun` entries. The `run_status: "waiting_workflow_choice"` branch (§3) is dead — the state machine in §4 C3 never sees a workflow because `process_exit`/`ttl_expired`/`reattach` events are all defined over the `runs` registry.
**Why it matters**: The proposal's §8 user decision explicitly locked scope to **A1 + A2/C**, and Phase C ("vessel_workflow_paused 渲染") was *folded into this work* as a first-class deliverable (proposal §8.2, contract §1 C2, §3 table). The contract presents `waiting_workflow_choice` as a contracted, three-end-aligned wire status. But the chosen reattach mechanism (runId-based, run-registry-based) structurally cannot deliver it. This isn't a minor gap — it's half the locked scope resting on an unroutable foundation. Locking this contract as-is would force a painful re-architecture mid-implementation (exactly what阶梯 lock is supposed to prevent).
**Why blocker**: contract mode + a wire/runtime claim that is false against real code = BLOCKER per the review brief. The contract's own §0 "ground truth" cites `vessel_workflow_paused` from protocol.ts:157 but never traced *how it's emitted/routed* — it assumed workflow ≈ run.
**Suggested fix**: One of:
(a) **Descope `waiting_workflow_choice` out of this contract** into an explicit follow-up contract that addresses workflow-reattach on its own terms (workflowId-keyed, since `vessel_workflow_paused` already survives disconnect — it's broadcast and the workflow keeps running server-side via `/resume`; the *actual* gap there is just iOS rendering, which is pure additive UI, no wire lock needed). Note in §8 that the proposal's "Phase C folded in" decision is honored at the *iOS rendering* layer but the *reattach wire* only covers cli-runner runs. This is the honest, minimal fix and matches the personal-single-user simplicity bar.
(b) If keeping it in scope: add a §4.5 explicitly modeling the workflow path as a *parallel* state surface keyed by `workflowId`, with its own reattach query (`reattach_workflow` or a `/api/vessel/workflows/:id` poll), and stop overloading `reattach_run`. This is heavier and arguably gold-plating for one user — (a) is preferred.
Either way the contract must stop claiming `reattach_run{runId}` resolves workflow pauses.

### F3. C5 disarm claim under-specified: the already-armed 590s `resolve("allow")` timer is owned by the closure, not the registry — detach must explicitly address it — [MAJOR]
**Where**: §6 C5.1 (`detachPermissionChannel(token)`: "仅解绑 send，保留 pending、不 resolve"); §6 C5.3 ("fail-open 仅在「有 attached 客户端但用户 590s 没点」时保留旧语义"); proposal I-9; the brief's load-bearing C5 timer-ownership question.
**Issue**: Fact-checked against `permission.ts:71-86`. When a permission `/ask` arrives, the 590s fail-open timer is armed *inside the Promise executor* at line 72-78 and stored as `entry.pending.set(requestId, { resolve, timer })`. The timer's callback **unconditionally `resolve("allow")`** after 590s regardless of channel state. C5's `detachPermissionChannel` as specified only "解绑 send" and "保留 pending、不 resolve" — it says nothing about the **already-armed timer**. So the contract's load-bearing security claim ("detached → no unsupervised auto-allow;挂起 until reattach or WAITING_DETACHED_TTL→expired") is **not guaranteed by the spec as written**: a permission that was armed *before* ws_close still has its 590s timer ticking; if reattach doesn't happen within 590s (and WAITING_DETACHED_TTL=120s is shorter, so usually the reaper fires first — but the reaper is `setInterval` every 30s on `run-registry`, a *different* module that has no handle on `permission.ts`'s timer), there is a window/ordering where the 590s `resolve("allow")` fires for an unsupervised, detached run. The contract asserts the outcome (no unsupervised allow) but the mechanism (who clears/re-arms the permission.ts timer on detach, and how the run-registry reaper reaches across module boundary to disarm it) is exactly the part left unspecified.
**Why it matters**: I-9 / NF1 is the *security* reason this whole contract is "评审高价值" (§12 says so). "detach disarms the 590s allow-timer" is the single most important runtime invariant and the contract states it as a consequence, not as a contracted mechanism with a named owner. Cross-module timer ownership (permission.ts armed timer vs run-registry reaper) is precisely where this will silently regress.
**Suggested fix**: Add to C5 an explicit sub-contract: "On `detachPermissionChannel(token)`: for every in-flight pending, **clear the existing 590s fail-open timer** and re-arm it as a *deny-or-suspend* timer bounded by `WAITING_DETACHED_TTL`, OR record `detachedAt` on the pending and have the run-registry reaper own a single source of truth for permission-expiry (and `permission.ts` exposes a `disarmFailOpen(token)` / `rearm(token, ms, mode)` API so the reaper can reach it without duplicating timer state)." Name the owner. Add a dogfood assertion (§11 item 3) that proves: arm permission → ws_close → advance clock past 590s → assert NOT resolved("allow") while detached.

### F4. C4 attached-but-zombie client (TCP half-open) has no TTL — unbounded-resource hole — [MAJOR]
**Where**: §4 C3 state table (`attached_running` row: "不触发，attached 不计 TTL"); §5 C4 reaper rules ("attached_running **不计 TTL**（有客户端在，长回合合法跑）"); §5 C3 硬规则.
**Issue**: The contract's resource-bounding story rests on: detached runs get `DETACHED_TTL`, waiting runs get `WAITING_DETACHED_TTL`, attached runs are trusted (a real client is watching). But "attached" here means "the WS `ws.on('close')` has not fired" — and TCP half-open / silent connection death (no FIN, no RST) is *exactly the failure mode the whole proposal is about* (proposal §0 step 3: "Software caused connection abort" only surfaces *after* iOS resumes; while suspended the socket is silently dead but `ws.on('close')` has not yet fired on the backend). During that window the run is `attached_running` in the new model → **never TTL'd**, **never abort()'d** (ws_close never abort by I-12), and the client may never come back (user kills the app while suspended). Pre-contract, `ws.on('close')` eventually fired and `abort()` reaped it. Post-contract, a zombie-attached run with no TTL bound can leak a live `claude` subprocess indefinitely until the OS tears the socket (can be many minutes, or never if keepalive is off). The contract's §3 failure-mode table (proposal §3 "detached run 服务端无上界 = 资源泄漏") fix only covers the *detached* state; it introduces a *new* unbounded state (`attached_running` + dead-but-not-closed socket) that the old code did not have.
**Why it matters**: This is a regression in resource-boundedness introduced *by* the contract, on the personal-single-user box where one leaked subprocess pinning CPU/Claude-quota matters. It's also subtle: it only bites when the socket dies without `close` firing — which is the canonical iOS-suspend scenario.
**Suggested fix**: Add a WS-level liveness probe (ping/pong or app-level heartbeat) so `attached_running` has a *liveness* bound: if no pong within `ATTACHED_LIVENESS_TTL` (e.g. ≤ DETACHED_TTL), transition `attached_running → detached_running` (which then gets DETACHED_TTL). Cheapest version: piggyback on existing heartbeat (`heartbeatRecordSpawn` is already called at index.ts:571 — there may already be infra). Document in §5 that `attached_running` is bounded by liveness, not literally untimed. Add dogfood: simulate silent socket death (no close event) → assert run still gets reaped within bound.

### F5. C3 race: `process_exit` during `reattach`, and abort SIGTERM-5s window vs `reattach`→status=aborted — [MAJOR]
**Where**: §4 C3 transition table (`reattach` column for `interrupting` → "回 status=aborted"; `process_exit` row; `completed_detached` "回 status=completed/failed + 清 record"); cli-runner SIGTERM→SIGKILL `KILL_GRACE_MS=5000` (cli-runner.ts:40).
**Issue**: Two unhandled interleavings:
1. **process_exit racing reattach**: §4 table defines `reattach` on `detached_running` → "→attached_running，重路由后续 sdk_message". But if the subprocess exits *between* the reattach message arriving and the backend installing the new send-channel, the `session_ended`/terminal record is written with no channel bound (the old `channelSend` captured the closed WS via the closure at index.ts:558-566; the new one isn't wired yet). The contract's §4 `process_exit` row distinguishes "若无人 attached" vs "若 attached" — but there's a third state during reattach handshake: *transitioning*. Not modeled → the completion can be dropped on the floor exactly during the recovery the contract exists to provide.
2. **abort 5s window vs reattach**: `client_interrupt` → `interrupting` → `abort()`. cli-runner does SIGTERM then SIGKILL after 5s (cli-runner.ts:40,233-246). §4 says `reattach` on `interrupting` → "回 status=aborted". But during that ≤5s window the subprocess may still emit `sdk_message`s (or even complete normally if it ignores SIGTERM and finishes first). The contract returns `status=aborted` immediately, telling iOS to write the aborted-terminal文案, while the backend may still send a real `session_ended{completed}` 5s later → UI shows "aborted" then a stale completion arrives → exactly the **UI↔transcript split (NF2)** the contract claims I-11/C6 prevents. C6's gate only prevents old-iOS-vs-new-backend split; it does *not* prevent new-iOS self-inconsistency from the abort-window race.
**Why it matters**: §9 I-11/C6 + the brief's NF2 question: "find any path where a mixed fleet still produces UI↔transcript split." Path 2 above produces a split *even on an all-new fleet* — it's intrinsic to returning a terminal status while the 5s SIGTERM grace is still live. The contract's state machine table is presented as exhaustive ("硬规则") but has at least these two unmodeled interleavings.
**Suggested fix**: (1) Add an `attaching` transient state (or make reattach atomic w.r.t. channel rebind before any status reply, and have `process_exit` during `attaching` queue the terminal record for the in-progress reattach to drain). (2) For the abort window: `reattach` on `interrupting` should return `status="interrupting"` (a 9th enum value, or reuse `running` with an `interrupting:true` flag) and let the *real* terminal `session_ended` drive the final UI state — never synthesize `aborted` on the client while the backend hasn't confirmed the subprocess is dead. Add dogfood case: interrupt + reattach within 5s + subprocess completes-instead-of-aborting → assert UI ends in exactly one terminal state matching the backend's actual `session_ended`.

### F6. Extending `run-registry.ts` (not a new module) — correct call, but `register()` call-site backward-safety claim needs the TS to actually enforce optionality — [MINOR]
**Where**: §1 C4; §5 C4 ("现有 `register()` 调用点 index.ts:570 传旧字段仍合法 → 新字段可选/默认").
**Issue**: Architecture-fit: reusing `run-registry.ts` rather than spawning a parallel module is the *right* call — it respects "Eva 优先复用" and the registry is already the cross-connection liveness anchor (index.ts:570 registerRun, :610 unregisterRun, :208 activeCount for /health). Proportionate, not a new abstraction. **However**, the contract's backward-safety claim is only true if the new `RegisteredRun` fields are declared `?:` optional *in the TS interface* — but §5's interface block declares `state`, `lastActivityAt`, `capabilityReattach` as **required** (no `?`). With those required, `registerRun(runId, { abort, cwd, prompt, startedAt })` at index.ts:570 **fails typecheck** (TS2741). The contract asserts "旧调用不破" (C4 兼容性 column: "新增字段全可选，旧调用不破") but its own interface contradicts that — `state`/`lastActivityAt`/`capabilityReattach` are exactly the fields the orphan manager *needs* non-optional to function, so making them optional weakens the reaper. The real fix is the call-site must be updated to pass them (it's a single call-site, trivially), and the contract should say so honestly rather than claim "旧调用不破."
**Why it matters**: contract mode = real-code standard. The compatibility column is factually wrong for the registry interface as drawn (required fields vs unchanged call-site). Minor only because the fix is a one-line call-site change with no external/wire impact (run-registry is internal, no third-end).
**Suggested fix**: Either (a) state in §5: "index.ts:570 `registerRun(...)` call-site IS updated to pass `state:'attached_running', lastActivityAt:Date.now(), capabilityReattach:<from C6>` — internal-only, no wire impact, not a compat break (registry has no external consumers)"; or (b) make them optional with documented defaults applied inside `register()`. (a) is cleaner and matches surgical-change discipline. Drop the "旧调用不破" phrasing — it's an internal interface, honesty > false-additivity.

### F7. `interrupt` global-scan fallback means `reattach`-carried interrupt may over-abort sibling runs — [MINOR]
**Where**: §4 C3 ("iOS interrupt() WS-down 分支… reconnect 后在 `reattach_run` 或独立 HTTP `POST /api/run/:id/interrupt` 携带"); OQ-A.
**Issue**: Existing `interrupt` handler (index.ts:475-482): if `msg.runId` present → `runs.get(runId)?.abort.abort()`; **else → `for (const h of runs.values()) h.abort.abort()`** (aborts ALL runs on the connection). The contract's WS-down Stop path queues `pendingInterruptRunIds` and replays on reconnect. If that replay ever sends an `interrupt` without a runId (e.g. the pending set is consumed loosely, or runId was never bound because systemInit hadn't arrived — CLAUDE.md invariant #8: sessionId nil pre-init), the fallback nukes every parallel run on that connection. With the contract's new "runs survive disconnect" behavior, a reconnect now has *more* live sibling runs than before (they used to all be abort()'d on close) → the blast radius of an unscoped interrupt is strictly larger post-contract. The contract doesn't constrain the replay to always carry a concrete runId.
**Why it matters**: CLAUDE.md pitfall #7 (per-conversation isolation) + invariant #1 (route by runId). An over-broad interrupt silently kills background conversations the user didn't stop — a parallel-routing violation, made worse by this contract increasing the number of survivable runs.
**Suggested fix**: §4 must require: `reattach_run`-carried / HTTP interrupt MUST always specify a concrete `runId`; the unscoped `interrupt` (no runId → abort all) path is forbidden for the reconnect/WS-down Stop replay. If runId is genuinely unknown (pre-systemInit), the contract should say it falls back to force-clear-local-only (no server abort) rather than broadcast-abort. Add dogfood: 2 parallel runs, WS-down Stop on run A, reconnect → assert run B still alive.

## Strong points

- **Direction is right and has not ballooned.** "Backend keeps run alive + reattach contract" remains the correct architecture now that the full surface is visible. The contract did NOT balloon past the proposal — it correctly *narrowed* (Phase B explicitly excluded, no seq-buffer, transcript-as-content-source reused, `--resume` reused). The 8-state enum is the proposal's 7 + `unknown`, justified by a real failure mode (backend restart → NF1/OQ-B), not gold-plating. For one user / one Mac this is proportionate; it is NOT distributed-systems over-engineering.
- **Reusing `run-registry.ts` over a new module is the correct, lower-debt choice** (F6 caveat is cosmetic). The registry is already the cross-connection anchor; extending it keeps one source of truth.
- **Wire additivity verified TRUE against real code**: `reattach_run` slots cleanly into `protocol.ts:19-69` ClientMessage union with no key collision; `run_status` is additive to ServerMessage `71-161`. The Swift `ServerMessage.decode` (Protocol.swift:159-161) `default: return [.unknown(type: type)]` — confirmed: an unknown server `type` does **NOT** decode-throw, it degrades to `.unknown` and is dropped (runId→nil). The contract's "旧端忽略未知 type" claim is **TRUE**. The Swift `ClientMessage` is `Encodable`-only (no Decodable), so adding a `reattachRun` case cannot break old decoding — also TRUE.
- **`status ?? .unknown` defense is sound**: making the Swift `RunStatus` a `String` raw enum with `init(rawValue:) ?? .unknown` correctly future-proofs against later enum growth — this is the right pattern and is consistent with the existing decode-defaulting style throughout Protocol.swift (every field is `as? T ?? default`).
- **C6 double-gate (flag + per-run capability stored on `RegisteredRun.capabilityReattach`) genuinely protects the old-iOS byte-identical path** for the *cli-runner run* case: an old iOS never sends `clientCapabilities.reattach`, so `capabilityReattach=false`, so `ws_close` keeps the current abort behavior for that run. NF2 split is genuinely prevented *for the runs path*. (The workflow path is F2's separate problem; the gate logic itself is sound.) Rollback = env flip, no redeploy — correct and matches single-user ops reality.
- **CLAUDE.md invariants respected**: pitfall #6 (PreToolUse hook untouched — contract explicitly says "不动 PreToolUse hook 机制"), #8 (`sessionId?` optional in `reattach_run`, contract cites invariant #8 correctly), #7 (routing stays per-runId, no global state introduced). I-1..I-10 inherited cleanly; new I-11/I-12 are well-formed and I-12's grep-based dogfood check is a genuinely good guardrail against ws_close→abort regression.
