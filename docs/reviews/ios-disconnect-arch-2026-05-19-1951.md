# Phase 1 Review — architecture-fit lens
> Reviewer: harness-architecture-review · Date: 2026-05-19 · Phase 1 (independent)

## Summary verdict
ACCEPT-WITH-CHANGES

The diagnosis is solid and code-verified; the 3-phase ordering (止血优先、零协议改动、复用现成件) is the right strategic shape for a personal single-Mac tool and does NOT over-borrow distributed-systems machinery in Phase A. But the proposal **understates the load-bearing risk in its own OQ2/OQ4**: Phase A's "completed-run replay from jsonl" rests on assumptions about the CLI transcript that are only *half* true. The jsonl is written by the `claude` subprocess (not Vessel), is streamed incrementally, but has **no terminal marker** — so "run finished vs run still mid-stream vs run killed" is undecidable from the transcript alone. This is fixable within Phase A scope but must be designed explicitly, not deferred to "复用 8min watchdog". Phases B/C classification is correct.

## Findings

### F1. Phase A's "completed-run replay" depends on a transcript terminal-state signal that does not exist — OQ4 is a real BLOCKER-class gap, not an Open Question — [MAJOR]
**Where**: §5 Phase A step 3 ("run 已完成→走 SessionsAPI.transcript 全量回放"), §8.1, OQ4
**Issue**: I fact-checked the load-bearing assumption. `cli-runner.ts` never writes the session jsonl (lines 2, 193 — the only `writeFileSync` is the temp `--append-system-prompt-file`; grep for `appendFile`/`.claude/projects` in cli-runner returns nothing). The transcript at `~/.claude/projects/<cwd>/<sid>.jsonl` is written **by the `claude` CLI subprocess itself**. I inspected a real 164-line transcript: it is streamed incrementally (interleaved `assistant`/`user`/`tool` entries with rising timestamps — good, this part of §1/§4 holds), **but it ends on a bare `assistant` entry with no `result` / `system/init` / `success` terminal marker** (`jq` for any terminal type returns none). Compare cli-runner's actual completion signal: `session_ended` is synthesized by **Vessel** in `index.ts:596-597` from `abort.signal.aborted ? "interrupted" : "completed"` — it lives only in the WS stream, never on disk. Consequence: an iOS client that reattaches *purely from transcript* (the §5 Phase A path) **cannot distinguish** (a) run completed normally, (b) run still generating (more lines coming), (c) run was SIGKILL'd mid-tool. All three look identical: "jsonl ends on an assistant message." §8.1's "复用现有 8min watchdog 语义" does not resolve this — the watchdog only fires after 8min of *no activity*; it cannot tell a 20-second-ago-completed run from a still-running one, so the user either waits 8min for a finished answer or the busy state clears while tokens are still being written.
**Why it matters**: This is the exact "恢复假设永远成功 / 无 fallback" failure mode the proposal itself lists in §3 row 5 — Phase A would regress into it. The proposal frames this as OQ4 ("busy 态靠什么清？") and §8 decision 1 (a "user decision"), but it is **author-resolvable and must be resolved before Phase A is implementable**, not punted to the user.
**Suggested fix**: Phase A must keep an explicit server-side run-state record (the detached run is still tracked in the `runs`/`registerRun` map per `index.ts:570` — `registerRun(runId, {abort, cwd, prompt, startedAt})` already exists). On reconnect, iOS asks the backend "is runId R still alive?" via a small **query**, not a transcript heuristic: alive → re-route its future `sdk_message` (the run object is still in memory, this needs zero protocol change — it's a reconnect handshake on the existing WS); finished/gone → backend returns the synthesized `session_ended` reason it would have sent, then iOS does the jsonl full replay. The transcript is the *content* source; the in-memory run map is the *liveness* source. Re-scope OQ4 from "open question" to "Phase A design requirement: server is the run-liveness oracle, transcript is content-only."

### F2. OQ1 is correctly identified but under-weighted: user-interrupt and ws-close share the *exact same* `abort.abort()`, and Phase A's decoupling silently changes user-Stop semantics — [MAJOR]
**Where**: §9 OQ1, §6 I-1
**Issue**: Verified. User Stop and connection-drop converge on identical backend code. `index.ts:475-481` (`interrupt` message → `runs.get(runId)?.abort.abort()`) and `index.ts:688-693` (`ws.on("close")` → `for (h of runs) h.abort.abort()`) call the **same `AbortController.abort()`**, which cli-runner's `onAbort` (cli-runner.ts:228-251) turns into SIGTERM→SIGKILL. There is currently **no signal distinguishing the two**. Worse, on the iOS side `interrupt()` (BackendClient.swift:399-409 / 413-420) has a branch: WS open → send `.interrupt`; **WS down → `forceClearRun` directly** (it relies on "backend already aborted on close"). If Phase A makes `ws.close` stop aborting, that iOS `else` branch becomes a **correctness bug**: user taps Stop while WS is flapping, iOS locally clears the run, but the backend now keeps the detached run alive forever (until the orphan reaper) — the user explicitly asked to stop and the run keeps burning. Phase A cannot land without simultaneously fixing BackendClient.swift:404-407 and 417-418.
**Why it matters**: This is a cross-end correctness coupling the proposal flags as an OQ but does not put in the §6 invariant guardrails or the Phase A "必改" list. A user pressing Stop and the work continuing is a trust-breaking regression for a Jarvis-style tool.
**Suggested fix**: Add to §6 a new invariant: **I-8 用户 Stop 必须真停**: `interrupt` message → real abort always (even when transitioning detached); only `ws.close` enters detached. And add to §4 ❌缺口 / Phase A 必改: "iOS `interrupt()` 的 WS-down else 分支不能再假设 backend 已 abort——必须改为 enqueue 一个 pending-interrupt，在重连后下发真正的 `interrupt`，否则 detached run 收不到用户停止意图." This makes OQ1 a resolved design constraint, not an open question.

### F3. The 阶梯/螺旋 classification is essentially correct, but Phase A's "解耦 run 生命周期 ↔ 连接" needs an anchor-gate sanity pass it is not given — [MINOR]
**Where**: §0 不可逆度 line, §5 Phase A ("无 wire 协议改动"), §10
**Issue**: I read HARNESS_ROADMAP §0.5. The 阶梯 list (lines 124-132) is: schema/migration, wire protocol, 6-layer boundary, runtime provider, permission/sandbox, worktree/ResourceLock, release strategy, iOS server-driven schema + MIN_CLIENT_VERSION. Phase A genuinely touches **none** of these wire/schema/migration anchors — it is a behavior change inside L4 Runtime (run lifecycle) reusing existing L2/L5 surfaces (SessionsAPI, jsonl). So "Phase A = 螺旋, Phase B = 阶梯 (contract+ADR)" is the **right** classification and the proposal's self-assessment is honest, not under-classified. However: §0.5 line 195's 7-question anchor gate includes "资源争用" and "rollback". Phase A introduces a *new lifecycle state* (detached run) + a *new background reaper* + changes the meaning of `ws.close` process-wide. That is the highest-blast-radius part of an otherwise-light change: it touches the shared `runs` map and the `vesselRuns`/`runIdToConversation` cleanup invariants (CLAUDE.md iOS invariant #2: "runIdToConversation cleaned on EVERY sessionEnded"). It does not need a full ADR, but it does need the §0.5 anchor-gate "资源争用 + rollback + 兼容(老 iOS 装机端)" three questions answered in the proposal before implementation — currently §3/§6 cover resource bound (I-1) but not rollback ("if detached-run causes a prod incident, what's the kill switch — an env flag reverting to unconditional abort?") nor old-client compat (an old iOS build that still runs `clearStuckRunsAfterReconnect` force-clear will now force-clear a run the backend kept alive → double-handling, the exact I-2 failure but cross-version).
**Why it matters**: Not a blocker for the proposal, but skipping these makes Phase A look more "free" than it is and risks a no-rollback-path landing.
**Suggested fix**: Add to Phase A: (1) feature flag `VESSEL_RUN_SURVIVES_DISCONNECT` defaulting OFF, so rollback = flip env + kickstart, no redeploy; (2) an explicit "old iOS client behavior" row — old builds force-clear locally but backend keeps run; document that the orphan reaper (I-1) is the safety net so it degrades to "wasted compute until reap", not corruption.

### F4. §8 framing — 2 of 3 "user decisions" are author-resolvable; only 1 is a genuine user call — [MINOR]
**Where**: §8 待用户拍板的决策
**Issue**: §8.1 ("孤儿 run 宽限窗口") — the proposal already self-answers ("复用现有 8min watchdog 语义"). Combined with F1, the *real* design (server is liveness oracle) makes the window question secondary: a completed detached run is reaped near-immediately on its natural completion, only a *stuck* detached run needs the 8min bound. This is an author design decision, not a user tradeoff. §8.3 (Phase C 折叠 vs 单独 backlog) is genuinely a user prioritization call — keep it. §8.2 (A only vs A+B) is also a real user scope call — keep it. So §8 should be 1-2 decisions, not 3, and §8.1 should move into the F1 design resolution.
**Why it matters**: Per CLAUDE.md / Karpathy-②③ and the project's "Interaction Questioning" boundary, presenting author-resolvable items as user decisions dilutes the user's actual decision and is the anti-pattern the harness explicitly guards against (don't push design choices up as "your call").
**Suggested fix**: Demote §8.1 to a §5 Phase A design note resolved by F1. Keep §8.2 and §8.3 as the only two user decisions.

### F5. Strong: §1's "Vessel already owns the heavy-tier assets" thesis is verified and correctly bounds scope — [FALSE-POSITIVE-CANDIDATE for over-engineering concern]
**Where**: §1 last paragraph, §4 ✅已就绪
**Issue (non-issue)**: I pressure-tested whether "backend keeps run alive after disconnect" is borrowing distributed-systems complexity unfit for single-user single-Mac. Verdict: **it is not**, *for Phase A*. The complexity (seq buffers / retention windows / resync) is explicitly quarantined into Phase B and *not* implemented. Phase A reuses: cli-runner `--resume` (cli-runner.ts:141, verified `if (resume) args.push("--resume", resume)`), the CLI's own incrementally-streamed jsonl (verified real transcript), iOS `SessionsAPI`/`TranscriptParser`. The only genuinely new server primitive is "don't abort on close + a bounded reaper" — that is the *minimum* viable change, consistent with Simplicity-First. The strategic direction is right: a personal long-running-agent tool **must** decouple run-life from a flaky mobile socket; that is table-stakes correctness (tmux/mosh tier), not enterprise gold-plating. Author must NOT let Phase 2/3 talk them into starting from Phase B.
